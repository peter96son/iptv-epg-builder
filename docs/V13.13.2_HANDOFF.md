# v13.13.2 — GitHub Actions stability + cache retention

## Confirmed problems

1. Both workflows used `github.run_id` in the cache key and saved a new ~810 MB
   cache on every run. No cleanup was performed, so 12 caches consumed ~9.5 GB.
2. Publish steps used a plain `git push`. If `main` changed during a long run,
   publication failed with `rejected main -> main (fetch first)`.

## Changes

### Cache
- Adds `actions: write` permission.
- Keeps run-specific immutable cache keys (required so changed `.cache` can be saved).
- After each save, queries the GitHub Actions cache API and retains only the
  newest **2** `epg-cache-${runner.os}-*` entries.
- `data/metadata.sqlite3.gz` is untouched and remains the durable metadata snapshot.
- `restore-keys` still restores the newest compatible cache.

Expected steady-state cache storage: about 1.6 GB at the current ~810 MB/cache,
instead of growing toward the 10 GB account limit.

### Git publishing
- Before every push, fetches current `origin/main`.
- Rebases the generated commit onto current main.
- `-X theirs` during rebase means the generated commit wins only when the same
  generated file conflicts; this prevents generated changes from being silently lost.
- Retries fetch/rebase/push up to four times if another update wins the race.

Applied to:
- Update EPG output push
- Worker audit push
- Backfill metadata push

## Important
The two workflows already share `concurrency.group: epg-metadata`, so they do not
run simultaneously with each other. The race repair mainly protects against
manual/user commits or any other writer changing `main` while a long job runs.
